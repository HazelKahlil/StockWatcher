# 存储规则：可追溯、可恢复，不让历史写入拖垮实时提醒

> 最后更新：2026-07-31 ｜ 适用：SQLite、repository、缓存、配置版本、备份、导出和迁移

## 硬规则（违反按 review P1；不可恢复数据损坏按 P0）

| 规则 | 为什么 |
| --- | --- |
| SQLite 使用 WAL 与短事务；长查询、导出和备份不得阻塞实时提醒 | 单机历史能力不能牺牲盘中延迟 |
| 每次提醒保存源/显示时间、三只、子分、处罚、板块、资金原值/质量、provider/config/app 版本和推送状态 | 没有完整上下文就无法解释、复现或评价提醒 |
| Schema 迁移必须有备份、前后校验和回滚/只读降级方案；真实数据迁移需人类确认 | 历史与反馈是长期评价证据，损坏后难恢复 |
| 配置版本不可覆盖写；启用状态和变更来源必须可追踪 | 排名规则变化要能回放和回滚 |
| 凭证、交易账户信息和密码不得进入业务数据库、导出或日志 | 数据库备份和日志会扩大秘密暴露面 |
| 保留和清理按交易日/配置执行并记录；磁盘不足时先停历史写入并告警，不让应用崩溃 | 资源耗尽应可预期降级，而不是破坏实时主链路 |

## 默认做法

- 提醒历史 31 天，反馈至少一年，盘后回顾只保留最近 31 个自然日，分钟缓存最近 4 个
  交易日，日志滚动 30 天，每日备份保留 30 份。用户主动下载到其他目录的 PDF 副本不由
  应用删除。
- 分钟缓存按日期分区；数据库与备份至少支持不同目录。
- 启动先做完整性检查；损坏时切最近备份或只读模式并显示红色状态。

## 反例

- 直接执行不可逆 `DROP COLUMN` 后再测试 → 正确：先复制备份，在样本库演练、校验并准备回滚。
- 为方便调试把 Bark key 写入 alert_event → 正确：只记录通道和结果，密钥放安全存储。
